# SATVA screening model — model card

**Model ID:** `satva-screen-dev-0.1`
**Status:** 🟠 **DEVELOPMENT MODEL — NOT VALIDATED FOR ANY REAL DECISION**
**Date:** 2026-09-04

---

## Read this first

This model was trained on **procedurally generated images**, not photographs of
real produce. It exists to prove that the SATVA pipeline — training, calibration,
ONNX export, quantisation, on-device inference, and the app's screening flow —
works end to end.

**It has learned nothing about real mangoes, bananas, papayas or tomatoes.** Any
number it produces about real fruit is meaningless. The mobile app displays
"development model" wherever a score from it appears, and the API records
`vision_model_kind` so a score's provenance travels with it.

The validation programme that would make a real model trustworthy is in
[`docs/validation_plan.md`](../docs/validation_plan.md) and specification §19.

---

## What the model does

| | |
|---|---|
| **Architecture** | MobileNetV3-Small backbone, two heads |
| **Parameters** | 1,074,978 |
| **Input** | 224×224 RGB, ImageNet normalisation |
| **Output 1** | `anomaly_score` — calibrated 0–100 |
| **Output 2** | `ripeness_index` — 0–1 |
| **Output 3** | `embedding` — 576-d, L2-normalised |

The backbone is shared between both heads (specification §3.5): one photograph,
one forward pass, two answers. The embedding feeds near-duplicate detection in
SATVA Watch.

### What the anomaly head is not

It does **not** detect calcium carbide. It cannot — a camera measures reflected
light, and carbide residue has no reliable visual signature of its own.

It is trained on the *morphological consequences* the specification lists in
§3.1: unusually uniform skin colour while the stem and calyx remain green,
speckled surface burns from direct carbide contact, unnatural sheen, and texture
lagging behind apparent colour.

Its only job is to decide whether a ₹5 strip test is worth performing. Every
downstream consequence in SATVA — publication, clustering, escalation — runs on
the chemistry, never on this score.

## Training data

| Source | Count | Role |
|---|---|---|
| `synthetic_dev` | 1,443 | Training and validation |
| `controlled` (simulated) | 317 | Held out for evaluation and calibration |
| **Total** | **1,760** | 4 crops × 2 classes, balanced |

Generated by `satva_ml/make_dev_dataset.py`. The generator renders the
morphological signatures above, and applies lighting, blur, noise and JPEG
variation **identically to both classes** so the model cannot separate them on
capture conditions.

### Replacing this with real data

Point `--manifest` at a CSV with the same columns
(`image_path,crop,cultivar,label,ripeness,source,captured_at`) and re-run. Set
`source=field` for market captures and `source=controlled` for the college-lab
ripening batch. Nothing else changes — `stratified_split` automatically holds
the controlled set out for evaluation, because it is the only data whose labels
come from a known treatment rather than an inferred one.

## Reported metrics — and why you must not quote them

| Metric | Value |
|---|---|
| Validation ROC-AUC | **1.000** |
| Validation recall @ precision ≥ 0.90 | **1.000** |
| Ripeness MAE | 0.089 |

**A ROC-AUC of 1.000 is a red flag, not an achievement.** It means the
procedurally generated classes are trivially separable — which is a fact about
the generator, not about the model's ability to screen produce. A real field
dataset will produce far lower and far more informative numbers.

The same degeneracy broke calibration: see below.

## Calibration

Temperature scaling (Guo et al., 2017) is fitted on the held-out set so that a
reported "70 out of 100" means what it appears to mean.

**On this DEV model, calibration was declined:**

```
temperature : 1.0  (not fitted)
ECE         : 0.3775  (uncorrected)
reason      : the calibration set is perfectly separable, so temperature
              scaling is ill-posed — the likelihood is minimised as T → 0
```

`satva_ml/calibrate.py` detects this and refuses rather than returning the NaN
that an unguarded optimiser produces. An ECE of 0.38 means this model's scores
are **badly calibrated** and must not be read as probabilities.

Per-crop calibration (specification §6.4) is implemented and will produce real
temperatures once the calibration set contains overlapping classes.

## Export and quantisation

Pipeline: PyTorch → ONNX (opset 17) → TensorFlow SavedModel (onnx2tf) → TFLite.

The calibration and L2 normalisation are folded **into the graph**, so the
Python and Dart clients cannot disagree about them.

### Quantisation results — measured, not assumed

| Scheme | Size | Band agreement | Mean drift | Max drift | Gate |
|---|---|---|---|---|---|
| `int8_full` | 1.31 MB | 80.0 % | 8.23 | 16.91 | ❌ FAIL |
| `int8_fallback` | 1.31 MB | 80.0 % | 8.23 | 16.91 | ❌ FAIL |
| **`float16`** | **2.10 MB** | **100.0 %** | **0.07** | **0.26** | ✅ **PASS** |

**Band agreement** — whether the quantised model puts a sample in the same
triage band (`not_suspicious` / `inconclusive` / `suspicious`) as the FP32
original — is the release gate, because that is the only thing Layer A's output
actually decides. Raw score drift is kept as a diagnostic.

**Deployed: `satva_screen.tflite` (float16, 2.10 MB).**

The file is named for what it contains. Shipping a float16 model in a file
called `_int8` would mislead every reader of this repository.

### Why INT8 failed here

Full-integer quantisation of MobileNetV3-Small's squeeze-excite and hard-swish
blocks is lossy, and the error accumulates through the backbone. On this model
the class separation lives in a ~1.5 logit-unit window, so the accumulated error
is enough to move samples across a band boundary — correlation between FP32 and
INT8 scores was only 0.845.

This is partly an artefact of the DEV data: a model trained on real, overlapping
field data will have different logit statistics, and INT8 may well pass then.
The comparison is re-run automatically on every export, so this is a measurement
rather than a permanent conclusion.

**Both INT8 files are retained** (`satva_screen_int8_full.tflite`,
`satva_screen_int8_fallback.tflite`) so the comparison can be reproduced.

Against specification §5.1's ~4 MB target: float16 at 2.10 MB meets it with
room to spare, and INT8 at 1.31 MB would beat it once it passes the gate.

### Output index mapping

The graph converter does not preserve output names — they come back as
`PartitionedCall:0/1/2` in an order that is not guaranteed. The export
**measures** the mapping and publishes it; the mobile client reads it rather
than assuming:

```json
{ "ripeness_index": 0, "anomaly_score": 1, "embedding": 2 }
```

## Known issues

1. **XNNPACK delegate fails to prepare** this graph (`node 139`). TFLite falls
   back to reference kernels, so results are correct but on-device latency will
   be worse than the <200 ms target until this is resolved. Verification
   deliberately uses reference kernels for this reason.
2. **Latency is unmeasured on real hardware.** No Android device was available;
   the <200 ms target is unverified.
3. **The Keras fallback export path does not transfer backbone weights** and is
   flagged as such at runtime. `onnx2tf` is the supported route.

## Intended use

**Appropriate:** demonstrating and developing the SATVA pipeline; deciding
whether to prompt for a strip test in a demo.

**Not appropriate:** any real assessment of food safety; any published claim
about accuracy; any input to a regulatory decision; any crop outside
`{mango, banana, papaya, tomato}` — the app refuses those rather than guessing
(specification §6.4, rule 15).

## Reproducing

```bash
cd ml
python -m satva_ml.make_dev_dataset --out data --per-class 220
python -m satva_ml.train --manifest data/manifest.csv --epochs 12
python -m satva_ml.run_calibration
python -m satva_ml.export
```

Seeded throughout (`seed=20260904`) and run with
`torch.use_deterministic_algorithms(True)`, so a reviewer can reproduce these
numbers exactly.
